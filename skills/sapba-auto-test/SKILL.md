# SAPBusinessAgents 自动测试

You are the orchestrator in the **current native Codex conversation**. Use available native file, terminal, browser, Computer Use and MCP tools as appropriate; this skill does not replace or narrow the host toolset. Do not start another Codex SDK, `codex exec`, or backend AI loop. The product under test keeps its own real Runtime chain.

Read [the execution contract](references/execution.md) when preparing or executing a test. Resolve the repository from the user's workspace or this installed skill's `repository.json`; never assume that this skill's directory is the repository. Use its `.venv` Python and `scripts/run.py` as the helper entrypoint. Reuse the platform's registered SAP/Skill capabilities, connection configuration and existing Runtime authentication. Do not ask the user to recreate a connection merely because a particular MCP tool name is absent.

## Select and generate

1. Run `inventory`. Discover current features, source references, Agents, workflows, tests and missing coverage. Do not treat an active Agent as accepted/executable. Existing `sapclawtestcase` principles apply, but its historical `sap_odata_agent` runner paths are not present in this repository.
2. Run `card --output <durable-absolute-path.html>` and render it inline using the host's visualization surface. Read the available visualization guidance before displaying it. Default selection is free-query, workflows and agent-management; all eight categories are selectable. If the host bridge is unavailable, accept the card's textual action in this same chat. Do not open a separate console or website.
3. On `prepare` with `selected` and `inventory_digest`, check inventory freshness. Inspect the selected UI and source contracts, generate realistic cases for **each applicable selected operation**, then pass a JSON cases file to `prepare --select ... --cases ... --inventory-digest ...`. The no-cases CLI seed is explicitly offline regression only and must not be presented as full coverage.
4. Cases must have distinct business scenarios, not different object IDs. Generate main paths, relevant invalid/boundary paths, and cancel/recovery for asynchronous features. Natural-language questions must use business wording. Freeze independent baseline queries, comparison rules, scope, dependencies and impact paths before execution. Never derive an oracle from the product's answer or implementation rules.
5. Display the generated coverage and a `card --plan ...` with **开始测试**. Selection, generation and saving widget state never start tests. Explicit user instructions to start may substitute for the button; do not ask twice for already granted scope.

## Execute in this chat

On a `start` action, verify the plan digest and reuse the card's `request_id` exactly (legacy text-only requests may use `start:<plan_id>`). A new intentional run after completion needs a new request ID; a response retry keeps the same ID. Active runs of the same plan are coalesced. `start` snapshots the actual working tree, including existing edits. Use `environment` and `target-marker` to prepare the disposable product target; start its API and site with native tools and the specified isolated directories. Bind verified loopback endpoints with `bind-target`. Never point lifecycle tests at the user's normal product instance.

For every round, drain **all** selected runnable cases before repairs. `run-round` runs deterministic cases and returns native-tool work without launching an AI. Use current browser/Computer Use tools for native cases, save screenshots, tool observations and typed assertions under the returned evidence directory, then `finish-case`. Prefer reproducible browser scripts when actions are known. Persist results promptly so context compaction or connection loss does not lose progress.

Before live cases, run `capabilities` and inspect available native tools. Prefer an existing approved platform read capability; `test_sap_read` MCP and the deterministic `sap-read --task ... --case ... --role ...` command are equivalent controlled entrypoints to the platform capability layer. The command accepts only a started task, selected case and frozen recipe role, never URLs or credentials. Absence of an MCP name alone is not a blocker. Follow optional sample → baseline → frontend execution → fresh anchor → deterministic comparison/finish. Sample values must come from verified receipts; use `$sample.Field` bindings. Do not use ad hoc HTTP requests directly to SAP, copied credentials or guessed object IDs. If all approved transports are genuinely unavailable, record the concrete cause and continue independent cases.

For a free-query-only suite, `bind-platform --task ... --site-url ...` can bind the task-owned frontend build to the existing configured local platform, preserving its real Runtime and authentication. This profile must enforce task-owned run/session IDs and the query-only write guard; Agent/workflow publication, account changes, external actions and unrelated runs are denied. It records the platform boot/source binding separately from the tested frontend source. Lifecycle suites still require a disposable API/data root. Finish environment/marker preparation before dispatching cases; keep shared-state mutations sequential.

To validate repaired backend code while the shared platform has user tasks, use `environment --task ... --reuse-platform`. It returns a real product bootstrap with isolated query records, referencing the existing platform SAP configuration and Runtime selection/authentication state in place. Start only its task-owned processes; do not stop shared tasks or copy credential files. Bind with `bind-target ... --native-identity`; the lightweight loopback identity checks the task token, actual source digest and isolated data directory without querying every SDK. The product retains real authentication/model/permission/acceptance gates.

Keep evidence bounded: check free space before dispatch, save screenshots at meaningful steps, and keep repeated read-only status polling out of full browser snapshots. The helper records `evidence_storage_insufficient` before dispatch when less than 256 MiB remains. Preserve previous evidence and immutable plans. A controller timeout never proves that an accepted product run stopped; reconcile its actual state and cleanup before another submission.

Lifecycle operations use only run-owned temporary objects in the disposable target. Test both allowed deletion and refusal when references/history prevent deletion. Product publication/acceptance gates stay intact. Mail sending, account changes and SDK replacement use explicit simulation fixtures; do not perform those real external actions merely to test the feature.

## Batch repair and finish

- An ordinary failing case is evidence to collect, not a reason to start editing. `begin-repair` is allowed only when the complete round has terminal outcomes.
- Classify failures before editing. Data gaps, changed SAP data, credentials, permissions and unavailable tools are blockers, not product defects. Group repeated failures by root cause and retain the original observations.
- Save the evidence-based groups with `diagnose`; environment/data diagnoses are excluded from automatic code repair. Original failure records remain unchanged.
- Repair product code in the returned **candidate source** directory, not the disposable lifecycle target or original checkout. Keep plan/oracle/acceptance requirements intact; do not delete cases, relax assertions, fake baselines or bypass gates. Already-executed suites, snapshots and evidence stay immutable. An obsolete fixture may be repaired in a new source revision, then `prepare --parent-task ... --revision-reason ... --cases ...` creates a fresh audited plan. It records changed fixture hashes and checks unchanged business recipes, existing assertions, exception expectations and parameterizations; review the diff for equivalent behavior as well. Never modify a frozen run in place. For a proven browser locator defect, `revise-locators` remains available with unchanged assertions, inputs and baseline.
- Run relevant unit regressions in the candidate, then `verify-repair`. It calculates failed/affected cases and prerequisite chains. Rebuild/rebind a fresh product target for the new round before browser cases. Drain the complete retest round before considering another repair.
- For a proven native response-collection defect, save the corrected host script in task evidence and use `revise-native` during repair. It creates a new immutable plan with unchanged cases and an audited script hash. Capture each actual mutation response before frontend navigation; never repeat a POST after uncertain delivery. Read-only polling may retry transient transport errors within the frozen deadline and must preserve timeout evidence. If Chromium requests local network access for the owned loopback origin, grant that scoped permission and record it; do not disable browser security or rewrite CORS.
- Default maximum is three batch repairs; a root cause with two non-improving rounds is reported and retired from automatic attempts. Other issues continue. Do not loop indefinitely.
- Run `begin-final`, complete the once-per-cycle selected-suite review, and `complete`. `apply` automatically applies the verified cumulative patch with conflict checks and recovery backups. Existing edits form the baseline; later user edits are not overwritten. Do not commit, push or publish the project.
- If the completed current round already freshly executed every selected case on the unchanged candidate, every result passed, and live comparisons are verified, `begin-final --reuse-complete-round` can freeze that complete execution as the final review. It checks current-round coverage, source/patch/script hashes and all recorded evidence. Audit the business results before `complete`; never fill current gaps with passes from older rounds. Otherwise use the default separate full-review round.
- Use `report` and show the resulting Markdown/JSON, failure groups, screenshot links and actual Diff. Distinguish live SAP, offline and simulated evidence and passed/failed/blocked/inconclusive/not-run states. A test report does not grant formal product acceptance.

For stop, call `cancel` and stop only task-owned processes. For resume, inspect status and reconcile active/unknown operations before dispatch; `resume --interrupted-case ...` preserves an unknown operation as blocked rather than replaying it. For “重测失败项”, use `retest`; it does not consume a repair batch.
