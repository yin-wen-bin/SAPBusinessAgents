# MCP 连接与本地服务切换

Git 提交、合并和推送不要求关闭 MCP。启动器在应用已经验证的新代码或受控重启时，使用 `sapba.mcp-maintenance/1` 协调本仓库的 MCP。

1. 在独立的短锁内关闭 MCP 工具调用准入。已经接收的调用持有共享操作锁，启动器在部署锁之外等待它们完成。不会取消或重放调用。
2. 取得独占操作锁后，启动器核对进程创建身份、精确模块、仓库、已审阅代码指纹，以及进程返回的本次随机挑战。只有全部符合的 MCP 及其实际祖先进程能够通过原有写入者检查。模块名称、PID、历史注册文件或过期应答均不足以放行。
3. 按原控制器执行任务空闲复查、源码和环境一致性、SDK 证据、监听进程身份、前后端版本核验和成对回滚。连接本身一直保留。
4. 成功切换或成功回滚后恢复调用；回滚未完成时保留维护屏障和原恢复日志。新调用得到 `accepted:false`、`retryable:true` 的维护错误，没有业务副作用。客户端可以在维护结束后提交先前明确未接收的请求；已经接收而结果未知的请求仍需按原任务标识核对。

`initialize`、`ping` 和 `tools/list` 继续响应。自动测试的显式取消使用独立工作线程，可在排空期间结束在途任务；取得独占切换锁后则明确拒绝。自动测试 MCP 的 SQLite 初始化也放在调用准入之后。Runtime MCP 只使用平台传入的 `SAPBA_STARTUP_REPOSITORY`，不猜测目标、不接受新凭据。单独仓库的 Codex 原生创作插件不属于本仓库的服务进程。

协调记录位于 `.local-data/startup/mcp/`，只含进程、协议、代码指纹和随机挑战，不存业务输入或凭据。它们不是权限凭据。未知进程、旧版 MCP、篡改记录、链接路径、无法确认的进程身份仍会阻断；不会自动杀死进程。

Ctrl+C 取消切换前的等待时，恢复调用且不停止在途任务。进程崩溃留下的 MCP 暂停记录仅在确认原创建身份已消失、且没有未解决的服务屏障或切换日志时才能自动清理。否则沿用显式 `recover-switch`；恢复同样需要维护握手。

首次从没有维护协议的旧 MCP 升级时，需要让 Codex 重新加载一次 MCP 进程。旧进程无法凭磁盘文件更新获得新协议，启动器不会将其无条件放行。安装新协议之后，后续兼容的服务切换无需关闭连接。MCP 自身协议若发生不兼容升级，仍需重新加载客户端；此时启动器明确报告未协调的进程 PID。

无更新的快速启动路径不会新增进程扫描、维护握手或后台监视。维护只在本次启动器调用确实需要切换服务时执行。

验证入口：`python -B -m pytest -q tests/test_startup_mcp.py`。它覆盖真实 stdio 进程在维护前后的同一连接、调用排空、拒绝新调用、随机挑战、PID 复用、未知写入者、并发启动、取消、遗留屏障及回滚故障。默认 `scripts/startup-update.py verify` 包含这些检查。
