# 服务范围、历史配置审核及后补证据重评闭环

## 本次已保存证据审核

审查仅使用2026-10-24五模型的已保存工具结果及2026-10-23本机只读核实材料，没有新模型、SAP或认证调用，也没有解密受限原始行。

### 发票服务范围

`API_SUPPLIERINVOICE_PROCESS_SRV` / `2.0` / `A_SupplierInvoice` 的完整已保存Schema证明 `InvoicingParty`、`CompanyCode`、`PostingDate` 等字段存在及类型，但未提供其与供应商账户角色等价的定义，亦未提供原账户行到发票头的完整关联证明。其服务目录记录为迁移seed，不能仅靠目录名称或字段拼写推定角色等价。

因此不登记全局或服务级 `Supplier → InvoicingParty` 授权映射，生产注册表保持不变。这不是“模型不兼容”的结论。缺过滤、猜测发票号及无可靠关联的明细读取仍拒绝。

最小补证有两条可选路径，不必同时收集：

1. 目标服务和版本的可信语义资料，明确原查询所指供应商账户在何种条件下等于开票方，列明替代开票方等例外及前置约束。注册后仍须核对完整元数据及实际约束；不能把有例外的角色关系登记成无条件别名。
2. 原范围内账户行与发票头的稳定复合键关联证据，保留公司、年度、单据／项目、原供应商及过账日期约束，证明完整覆盖且无歧义。不能只提供一个发票号，也不能只挑能通过的记录。

上述材料可以是已有可审核导出／归档，不要求本轮访问SAP。已有字段存在性证据不需重复采集。

当前简单映射执行器不支持任意条件表达式；若补证仅能证明有限条件下等价，须先实施并测试受控条件／关联验证，不能只在注册JSON中附加一段条件文字就启用映射。

### 历史配置适用性

已保存K/F材料核实的是当前 `I_SPECIALGLCODE`：K/F为不更新余额的备忘项目。原核实文件明确声明 `current_configuration_only=true`、`historical_configuration_as_of_2022_proven=false`。其原始行受限且保持加密，不转为普通模型可读来源。

从本批已保存账户行提取的最小待覆盖日期为：

| 账户类型／标识 | 公司范围 | 实际过账日期 |
|---|---|---|
| K/A | 1710 | 2019-10-11、2020-10-26 |
| K/F | 1710 | 2019-10-11、2020-10-26、2021-10-26、2022-11-01 |

最小补证不是重查全部历史，而是：对应SAP系统／客户端及适用组织范围、K/A和K/F的分类属性、覆盖上述日期的有效区间或逐日适用证明、可核验来源与完整性。可使用历史配置快照配合变更记录／传输记录证明区间；当前快照本身不能证明历史未变化。若配置为跨公司层级，需明确证明其适用范围，不能伪造公司字段。

已有K/F当前属性、只读执行证明及制品摘要可以复用，不需重采；缺的是历史有效性，另缺K/A对应历史证明。受限材料须通过已批准的受保护读取适配器产生平台证明，不能让模型自报verified或在本轮直接解密。注册来源前仍须审核连接／系统归属、字段类型与原授权。

## 追加重评的实现

1. 共享Broker从本作业的成功读取中核对配置来源注册、证据归属、文件内容摘要、完整性、字段及公司／日期适用性。
2. 使用原始不可变业务证据和冻结来源契约本地重评，不发起任何查询。原读取输出、旧错误及旧报告不变。
3. 回执绑定运行、冻结报告契约、来源调用／证据／计划、旧评估摘要、配置证据及其代次；新摘要继续绑定原来源证据，避免把不同数据集因汇总相同而合并。
4. 正式报告预检使用新评估；只有报告原有全部校验通过，才将回执追加到该次报告验证记录。模型仅收到安全引用，不能通过请求参数上传或授予回执。
5. 共用最终收尾及验收比较器读取服务器保存的回执，核对归属、摘要及不可变粒度。无回执的历史结果保持旧含义。
6. 收尾前再次本地计算当前代次。报告之后若出现新／冲突证据，旧回执不能静默收尾，要求重新验证报告；不自动重发查询或模型任务。普通证据评估、权限、范围、来源锚点和发布门禁仍保留。

收尾核对绑定终态实际引用的validation_ref，不借用另一份较新报告的回执。SDK清理后工具能力已关闭，平台可以只读核验已保存回执，但不能发布新回执、开放晚到工具或恢复任务；取消或已持久化结束的运行仍拒绝。

金额工具的内容缓存同时绑定配置证明代次。同一tool_call_id重传恢复原调用；新的显式本地计算在新代次下生成新计算引用，旧计算记录保持不变。金额校验发现money_calculation_changed时只提示本地重算及重新绑定，不重查SAP、不重发模型任务，也不静默升级旧引用。

SHA摘要只是变更和关联检查，不是授权令牌或业务PASS。旧已结束任务不因新代码而恢复，不将新回执补写到旧PASS，也不跨运行借用证据。不同来源／重叠读取仍需原关联映射，不能用重评消除粒度或完整性问题。

## 离线回归

`tests/test_source_reassessment_closure.py` 覆盖两个Provider、后补有效证据、当前配置误用、公司不符、冲突追加、重复请求、旧读取不变、回执篡改／跨运行、最终收尾及真实验收比较器。独立基线和候选各自读取合成证据，不借用对方结果。真实配置来源和服务映射未因此批准。

## 受控上线方案（本轮不执行）

1. 冻结候选源码、注册表、测试报告及保护基线，确认无未记录变更；保留当前API／前台／worker与回退制品。
2. 新组件进入完整执行依赖，审核目标接入认证和实际模型协议影响；不修改摘要算法、不改旧证书或PASS。若包含上一轮尚未上线的worker变更，使用对应新不可变release，不能覆盖当前环境。
3. 已有有效证据仅在绑定条件确实适用时复用。确需真实轻量检查时另行授权；本轮不调用模型补证，不重跑15项。

   仅新增主机侧重评逻辑不应默认触发模型重验；须比较实际SDK协议、环境与现有结果的绑定。若待上线集合还包含前一轮worker／Schema变化，按真实差异审核，不能据本轮没有新增worker改动而忽略前一轮尚未生效的差异。
4. 确认相关活动任务、旧写入者及待清理进程退出，取得维护锁及屏障后再次确认，再成套切换API及对应必要制品。不能借上线取消用户任务。
5. 上线后仅通过允许的GET核对版本、配置、目录及历史读取；不启动查询、Campaign或补证任务。前端本轮未改，不需要独立切换或重建。
6. 失败时回退代码和制品，保留追加回执与原始记录。旧版本若不能识别新回执，应先验证其失败封闭性，不恢复可能忽略回执并误授权的旧写入者。

缺少目标接入／协议证据时停止正式切换；服务映射及历史配置仍未批准时保留明确业务阻碍，不以新重评机制制造通过。
