# Runtime admission

The shared internal request freezes the selected Provider, operation, permission
mode and (where supplied) existing Runtime binding and deadline. Free query
obtains its snapshot in the same synchronous preparation boundary. Codex and
callers without operation metadata retain their original strict adapter path.

WorkBuddy checks the installed immutable release, core integration evidence,
the requested SDK operation/mode, the selected model and authentication binding.
The derived certificate lookup and job-document deduplication exist only within
one owner-bound synchronous inspection. Critical files and evidence are checked
again at its closing fence. It never crosses a thread, await, queue or dispatch.
No display result or cross-request authorization cache grants execution.

After capacity is available, dispatch still checks installation, operation,
authorization, enablement, site/account revision, cancellation and deadline.
The native SDK connection and model waiting time are separate from admission.

## Unfinished job journal

`workbuddy_job_index.py` owns `sapba.workbuddy.unfinished-jobs/1`. Activation is
an explicit maintenance operation with stopped-writer clearance, not a GET side
effect. All host job writes use index-then-job locking and atomic replacement.
A dispatch declaration is durable before process creation. Only a persisted
terminal with confirmed cleanup removes an entry. Historical terminal records
and qualification evidence are not rewritten to build an index.

A dirty transaction, missing record, digest mismatch or unknown process identity
blocks admission. Explicit maintenance recovery may reconcile an unfinished
record only after its recorded process birth is proved absent; it records the
resolution. Never kill an unverified PID. Rebuild failures are not interpreted
as an empty queue. Do not restart an old journal writer after activation.

## Authentication

Unchanged official-cache observations do not launch another authentication
check. Concurrent WorkBuddy checks with the same frozen context share one
official check; each caller still verifies its own binding. Cancellation of a
waiter does not cancel that check. Changed contexts cannot share a result.
No automatic login, account switch or business query retry is introduced.

## Draft candidate checks

The authoring precheck invokes the same `candidate_business_output_issues`
function as save. It catches a technical-only SAP draft before attempting to
apply it; identity, revision, permissions and transaction checks still run on
save. Neither an offline test nor a saved revision is formal SAP acceptance.

## Validation

Use synthetic adapters and an owned local test worker. Benchmark one cold and
at least twenty warm preparations on the same machine, reporting installation,
evidence/authentication, unfinished-job checks and their read counts separately
from SDK connection. Preserve Codex configuration and all historic PASS records.
The 50 percent P50/P95 reduction is an acceptance target, not a reason to remove
checks. Real draft authoring is a separate, explicitly authorized validation.
