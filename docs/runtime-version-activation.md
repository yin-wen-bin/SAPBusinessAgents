# Python 依赖环境与版本激活闭环

普通双击现改为只使用已激活组合，不再扫描工作区或准备更新。已授权修改的测试、激活和验活须在本次交付收尾完成，详见 [启动与激活操作规范](startup-and-activation.md)。SDK显式更新仍复用本文的独立环境与激活机制。

## 状态与边界

已完成离线回归，并于 2026-10-28 受控更新 API 和系统配置页；没有升级 SDK 或建立新安装环境。原 `.venv` 通过明确审核的官方制品证明登记为原环境，SDK／CLI／worker 未变。安装通过、接入认证、模型兼容和业务 PASS 是不同事实。本方案不修改认证、权限、模型终态、SAP 范围或业务验证算法。上线记录见 [受控交付报告](runtime-version-activation-deployment.md)。

后续明确发起 Codex 更新时，在新环境完成安装与审核后，由现有启动器等待空闲并受控激活。WorkBuddy 继续使用原独立环境、验证与恢复流程；新增请求编号只提供去重，不取消其原有确认规则。

## 权威记录与职责

- API 仍以 `.local-data/startup-api-current.json` 和 `startup-api-previous.json` 为当前／回退组合。记录兼容增加 `environment`，包含最终路径、Python 与基础解释器哈希、配置、安装清单、内容绑定及依赖锁摘要。
- 前台仍使用 `site-builds/current.json` 和 `previous.json`，单独切换。联合切换只在原维护操作记录中关联两者。
- `sdk-update-jobs/codex/<operation>.json` 是更新收据，不是活动版本指针。它记载原组合、候选组合、请求、进度及错误，不能授予执行资格。
- `startup/pending-switch.json` 是当前启动事务的恢复日志，不是新的候选发布台账。停止旧进程前写入，确认健康／绑定并提交指针后移除。
- 健康响应的 `startup_binding` 由实际启动进程一次性生成，兼容增加 `environment_digest` 与解释器；不能通过重读磁盘伪装运行版本。

现有 `.venv` 首次受控登记时必须匹配已批准源码的原依赖证明。旧环境保持原位，不原地更新、不复制或移动虚拟环境；证明不一致就阻断。只改源码或前台时复用环境。

## Codex 安装闭环

1. 显式更新冻结目标版本、原运行组合和配置／账号修订。相同 `requestId` 与正文恢复同一操作，不随当前默认值变化重新安装；同编号不同正文冲突。
2. 复用现有 PyPI 下载、完整制品哈希和本地 pip 解析；原环境只用于只读解析，不执行安装。保留 1800 秒下载及 300 秒安装阶段预算，清理规则不变。
3. 冻结源码中的项目约束与精确制品锁分别验证。以已验证环境的包集合为基线，只有目标 SDK 和必要传递依赖可变化；不把 `pip freeze` 当作兼容证明。
4. 在最终路径 `api-environments/<operation>` 创建新环境，禁止系统包继承。精确制品锁执行离线、带哈希安装和 `pip check`；核对 SDK／CLI 元数据与导入来源，不启动 SDK 客户端。
5. 绑定文件内容，包括 RECORD 之外的导入钩子和脚本。外部更改不得通过重新计算绑定自动获准。容量不足在安装前阻断，不自动清理历史环境。
6. 复用原冻结源码，只替换依赖绑定，产生新的源码＋环境组合。目标现有接入证据不足则保留“待审核”；不自动登录、调用模型或执行 15 项验证补证。
7. 经一次性同用户独立执行器交给现有启动器。执行器通过账号 SID、PID 创建时间、命令和祖先关系核验；双方握手未确认，旧服务不能停止。握手使用启动器既有 90 秒引导界限，不延长安装或任务预算。
8. 等待空闲不持切换锁；取得部署锁和维护屏障后再次核对活动任务、其他 SDK 维护、旧写入者、清理、配置及证据。最后才停止属于本次项目且创建标识一致的旧进程。
9. 新 API 健康、源码与环境绑定确认后提交当前记录；“候选已准备”不显示为“已生效”。

支持声明目前保留历史项目版本 0.147.0 和已有安装审核覆盖的 0.162.0／0.163.0；安装约束为 `>=0.147.0,<0.164.0`，并要求精确审核列表匹配。区间中其他版本并不自动获准，更不表示支持任意最新版。新增版本需要独立审核支持约束及目标接入证据；页面可显示软件源新版本，但缺证时不能激活。

## 恢复与回退

- API 回退必须恢复原源码和原环境，不使用调用启动器的解释器。前台独立更新失败只恢复前台。
- 服务重启后的 GET 仅返回原操作及待核对投影，不重新安装或自动重派切换。
- 已有候选可通过现有 `update-operations/<id>/recover` 恢复。先核对原操作／配置、候选内容和独立执行器是否仍在运行；不重复安装。
- 存在未完成启动事务时，网页恢复保持阻断。由受控维护调用原启动器的内部 `recover-switch` 入口，核对原日志和实际进程后完成提交或恢复原组合。未记录 PID 创建标识、未知监听者、配置变化或清理不确定时保留阻断，不盲杀进程。
- 所有回退保留历史 PASS、新收据、旧环境和诊断；本轮不做环境回收。

## 接口与页面

已有更新 POST 兼容接受 `requestId`、`expectedTargetVersion`。新前台必须携带；旧客户端仍可不传并获得异步操作响应，不再原地安装 Codex。

准备中、待审核、等待空闲、切换中、已生效、失败／待核对使用原操作字段。安装成功但未激活仍显示旧活动版本。请求响应未知或 API 重启时只读取原状态，不重新 POST。切换 Tab、展开维护和普通刷新不触发更新。

原 WorkBuddy 升级可能执行已明确确认的认证与兼容验证；这是已有独立流程，本次没有在真实环境调用。Codex 新候选链路不把展示状态作为认证或执行资格。

## 原受控上线方案（实际执行结果见交付记录）

1. 冻结此次源码与前端构建，保留现有脏工作区中的其他成果，不混报为本轮修改。
2. 审核目标执行依赖的接入证据。本轮新增环境绑定、启动器和更新模块可能使原基础设施证明不再适用；不调整证书摘要算法、不改写历史或自动补跑验证。
3. 在状态副本验证 `.venv` 旧环境登记。证据不足或实际包与旧证明不同，停止部署并列明缺口。
4. 无活动任务、其他维护写入者和待清理进程后，以现有维护锁切换代码；本次部署本身不安装任何新 SDK。
5. 仅用健康、版本和配置 GET 核对源码／环境／前台实际绑定。真实升级另行发起。
6. 若激活失败，按原事务恢复配对源码与环境；前台按是否被改变独立恢复。不能回退到会对已登记活动环境原地安装的旧写入者。

离线验证与性能报告见 `.local-data/activation-offline-20261028/`。性能区分只读指纹核对、模拟热启动和真实服务启动，不能用模拟耗时代替实际上线验收。

### 本机旧环境演练阻碍（2026-10-28）

对现有 `.venv` 进行只读登记演练时，原批准记录的 METADATA／RECORD 绑定匹配，但进一步核对 2,801 个已记录文件，发现一处不一致：`codebuddy_agent_sdk-0.3.247.dist-info/WHEEL`，RECORD 声明 87 字节，实际 94 字节；哈希也不同。文件最后修改时间为 2026-08-29 08:33:06 UTC，早于本轮。具体历史修改原因尚无证据，不能仅凭版本号或当前内容重新计算摘要并承认可信。

这是 API 旧 `.venv` 的包元数据问题，不是对 WorkBuddy 当前独立 worker 或历史业务 PASS 的否定。本轮没有修改该文件、登记正式环境或切换服务。实际部署前需取得同版本原始分发制品及其来源／哈希，核对这处差异；若不能证明当前环境完整，则需另行授权准备干净独立环境并审核，不覆盖旧环境、不直接改 RECORD。新候选环境的完整性门禁保留。
